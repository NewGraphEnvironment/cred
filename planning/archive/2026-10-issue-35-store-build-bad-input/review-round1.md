## Findings

- **[severity: fragile]** R/store.R:1666-1668 (the `flush()` in `.crd_ingest_prepare`, and the roxygen saying "lines from parallel workers do not interleave"). One `cat(file = log, append = TRUE)` per document is atomic only while the block is at most 4,096 bytes. Above that, stdio sends it as more than one `write()`, and a concurrent worker's block can land between them, in the middle of a line.
  - Measured: 4 R processes each appended blocks with `cat(..., append = TRUE)`. Blocks of 3,060 and 3,978 bytes produced 0 corrupt lines out of 48,000 and 62,400. Blocks of 4,131 bytes produced 1,969 corrupt lines out of 64,800. Blocks of 6,120 bytes produced 1,232 out of 48,000. The corrupt lines are spliced mid-record, for example `C\tCCC…CA\tAAA…`.
  - When it happens: a note line is about 150-250 bytes (a Zotero storage path plus kind plus detail), so about 20 or more split or dropped chunks in one PDF crosses 4 KB. Dropped chunks carry the 400 message and come up to about 30 per chunk when a refusal persists down to the 64-character floor.
  - What it costs: another worker's line is absorbed into this one's `detail`. If the absorbed line was a `skipped` note, `.crd_store_ingest()` puts that PDF in `unsaid` with the reason "not ingested; see ragnar's warning". But the warning was muffled as `cred_ingest_skip`, so the user is sent to a warning that never printed, and the real reason is lost. Split and drop notes are misattributed or lost the same way. No store data is lost.
  - Remedy: one notes file per document, for example a per-call `tempfile(tmpdir = <dir>)` created in the worker, read and bound after ingest.
  - **Rule:** code-check-shell.md "Parallel writers sharing one output file interleave mid-record" ; code-check.md "A guard that fails toward pass" (the "A comment stating a property is an unexecuted claim" paragraph)

- **[severity: fragile]** Prose claims that ragnar 0.3.0's code contradicts. Each is a statement about an external system that a later reader will act on.
  1. research/ollama-embedding-context.md:52 says "The v2 `chunks` table is keyed on `(doc_id, start, end)`". CLAUDE.md:300 says "ragnar keys `chunks` on `(doc_id, start, end)`". The roxygen at R/store.R:1681 says "ragnar's `chunks` table keys on `(doc_id, start, end)`", and the test comment at test-store-build.R:177 says the same. In `ragnar:::ragnar_store_create_v2`, `PRIMARY KEY (doc_id, start, "end")` is on the **`embeddings`** table, and `chunks` is a `VIEW` joining `documents` and `embeddings`. Anyone looking for the constraint on `chunks` will not find it.
  2. research/ollama-embedding-context.md:50-51 says "The main process retries up to 20 times within 180 s". `ragnar_store_ingest` sets `max_tries = max(n_workers * 3L, 20L)`, and its default `n_workers` reaches 8, which gives 24. The roxygen at R/store.R:1686 says `prepare` turns retries back on "as the main process has them", but it hard-codes 20. That is equal only when there are 6 or fewer workers.
